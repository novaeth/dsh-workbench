# FOR-DEV：给开发者的文本

读者只在排障时读。他要的是原文，不是安慰。

## 三条

1. **原文**：日志、stderr、堆栈、命令不翻译、不美化、不总结。
2. **可检索**：保留错误码、路径、ID、时间戳、`file:line`。
3. **不进主句**：这些内容出现在终端用户界面时，只能在 `detail` / 折叠区 / 日志；主句不依赖它。

## 各面

### 日志

- 一行：时间（需要时）+ 目标 + 发生了什么。
- 关键值原样：ID、路径、退出码。
- 不写“出错了”这种没有定位信息的句子。
- 例：`[dsh-workbench] <target> 装上了，但这一版要重启一次 dsh 才生效（dsh 那边给的理由：<why>）`

### `detail` / 折叠原文

- 标注这是什么：原始输出 / 堆栈 / 命令 / 上游响应。
- 原样放；不截断关键错误行；截断要说明。
- 不复述主句，不加“请”。

### CLI 输出

- 一条：规则号 / 判据名 + `file:line` + 一句修法。
- 通过 / 失败用稳定前缀；退出码单独给。
- 不装饰、不排版成散文；agent 也会读，要能照做。
- 例：`[S16] src/host/service.ts:42 文件 240 行，超过上限 200 —— 拆，或传 fileLines`

### 安装命令

- 与主句成对：主句说“装什么、为什么”，下一行原样命令。
- 命令不翻译、不换行、不拆成散文。
- 用户要复制它，所以命令块里不放解释。

## 边界

- 终端用户会看到原文时，折叠并标注；不要让主句依赖它。
- 安装命令是唯一允许原文直接出现在用户面前的情况，且必须配一句人话。
- 不给用户看堆栈；需要定位时给错误码 + 一条修法。

## 验收

1. 日志能 grep 到对象与原因。
2. `detail` 里的路径 / 码 / 命令原样，能直接对照。
3. CLI 一条能照做；失败带 `file:line`。
4. 人侧主句里没有原文。
