# 架构

一句话：**dsh 是本体，工作台是外壳，面板能力是模块。** 外壳不改 dsh 本身，只换外面的那一层。

## 层

```
dsh（本体：会话、工具、审批、插件表）
└── 外壳 packages/core   左栏 + 常驻对话 + 右侧数据面板
    ├── 域 packages/*/src/modules/*      一个域一个视角
    └── 模块（别人发布 / agent 现做）    一张卡一份能力
```

外壳与共享契约分成三个包：`@dsh-workbench/core`（外壳）、`@dsh-workbench/shared`（契约、
哑组件、i18n）、`@dsh-workbench/module-tools`（模块的 build / check / lint / init）。

## 两个运行时

宿主侧与浏览器侧是两条链，**不许互引**：

- 宿主侧：`packages/core/src/shared/api/host/**`、`src/modules/*/model/**`
- 浏览器侧：界面、组件、hooks

判据会顺着 import 图走一遍，越界就红。理由很实际：宿主侧的代码能碰文件与进程，
浏览器侧的代码不能；混在一起，出错时你分不清是谁干的。

## 单元协议与槽位

一个模块声明自己的 `unit`、卡片顺序、要注入的工具与宿主能力。外壳按槽位把卡片放进去，
模块不自己决定位置 —— 位置是外壳的语义，不是模块的。

## 数据通路

面板**只读**。数据从宿主侧的读接口出来，经共享契约的类型进到浏览器侧，渲染成卡片。
没有任何一条路径是从面板写回去的；写入永远走 agent 工具。

## 门禁是一条链

类型 → lint → 覆盖率 → 架构红线 → 文档 → 运行时隔离 → 接线自检 → 模块判据 → 发布产物。
一条链，两个入口（仓库根与包内）跑的是同一份，`pnpm release` 的闸也是它。

其中几条值得单独说：

| 判据 | 盯什么 |
| --- | --- |
| 架构红线 | 层序、目录契约、唯一出处、令牌、反退化 |
| 运行时隔离 | 两个运行时互相 import 就红 |
| 接线自检 | 槽位名、key、id、locale —— 语法检查抓不到的那类错 |
| 发布产物 | 出货的文件里不许有夹具 |

## 零注释

全仓代码不留注释（`.ts` / `.tsx` / `.js` / `.mjs` / `.cjs` / `.css`），唯一例外是公开入口
的成员可以贴导出的 JSDoc。为什么这样定，写在仓库的 ADR 里。

配套的是命名与结构：一段代码读不懂，先改名字和切分，不是补一句解释。

## 想读更深

`ARCHITECTURE.md` 是这套东西的完整版（层序、协议、槽位、数据通路、每条判据的由来），
在仓库根目录。给模块作者的手册在 `packages/core/skills/workbench-module-diy/`。
