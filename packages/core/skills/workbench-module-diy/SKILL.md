# workbench-module-diy

## 第 0 步：判去向（分诊）

先判这是哪一类会话，再打开首读文档。流程外的入口不进入六步流程，也不写设计记录（底稿）。

| 去向 | 判据 | 首读 | 终止点 | 审批 |
|---|---|---|---|---|
| **现成的** | 模块市场已有、本机已安装但未显示，或 dsh 已有能力（含定时） | [FAMILY.md](FAMILY.md) 的工具选择 | 安装、显示或直接使用后交付，不开流程 | 外部安装等按工具要求；显示已有模块不审批 |
| **一次性** | 只处理这一次，不要求以后按同样步骤执行 | 要判断是否固化时读 [WORKFLOW.md](WORKFLOW.md) §1；否则直接执行 | 结果进对话；不建模块、不写设计记录 | 沿用所调工具的审批 |
| **改道** | 要改 dsh 本身，或需要新账号、新凭据、新服务、新依赖 | 不读流程；指出创造模式或工程域 | 给一句指引和一个现在就能用的替代后停止 | 不发起模块方案审批 |
| **看板**（`board`） | 用户要在面板上持续看到内容、状态或动作 | [FLOW.md](FLOW.md) 的建看板流程 | 安装、验收、保存设计记录并交付 | 方案确认及写操作按跨入口规则 |
| **无看板**（`headless`） | 要持续跟进或代办，但用户不看面板 | [FLOW.md](FLOW.md) 的无看板变体 | 交付工具与触发者，实际运行一次后保存触发与运行记录 | 方案需要批准；写操作仍审批 |
| **改已有**（`tweak`） | 用户要改动某个现有模块，而不是只查原因 | [FLOW.md](FLOW.md) 的改模块流程 | 只改并验证本次范围，保存设计记录 | 修改方案确认及写操作按跨入口规则 |
| **查** | 用户要「为什么 / 对不对 / 发生了什么」的结论 | [SYMPTOM.md](SYMPTOM.md) 的对应症状 | 说清结论与证据；查的过程不改源码 | 默认只读；真实交互或录制按工具要求 |
| **发布** | 用户明确说「帮我发布」或更新已发布信息 | [WIRING.md](WIRING.md) 的发布段 | 补齐材料、让用户看到发布内容并完成发布 | 发布需要审批；用户接管时等待 |
| **管理** | 安装现成模块、收起模块、停止长任务，或更新、换实现、管插件与来源、调顺序 | [FAMILY.md](FAMILY.md) 的工具选择与管理边界 | 可用工具完成，或转普通会话；不开建设流程 | 收起与显示不审批；其余按工具要求 |

「查」与「改」都可能像时，**先查，查完再决定要不要改**：要结论去查；要改动去改；「这个数不对」先按「数错」取证，确认是需求变化后才转改模块。

判是否需要模块只看工作台独有能力的正面清单，不问「脚本能不能做」：卡片与五种状态（五态）、面板行提示与顺序、动作路由、长任务六种状态（六态）与人工介入、按工作区的配置与数据目录、站点表、流程引擎、模块市场、工具包。再用三道测试：

1. **剥离**：卸载工作台后需求仍在纯 dsh 成立，就走 dsh 侧。
2. **触碰**：一项独有能力都没碰到，就走 dsh 侧。
3. **目的**：独有能力只是附带手段时，剥离后再判断。

不确定时往轻处错：先一次性或先无看板。判成一次性就给一句时间承诺，完成后把结果发到对话中；判成改道就停止，不创建模块。

## 流程选择

| 会话 | 走哪条 | 怎么开启 |
|---|---|---|
| 建看板 | [FLOW.md](FLOW.md) 的六步建看板流程 | `workbench_diy_plan` 先交去向与一句话复述；方案步交完整方案 |
| 建无看板 | [FLOW.md](FLOW.md) 的六步无看板变体 | 同上，方案与验收按变体替换 |
| 改已有 | [FLOW.md](FLOW.md) 的五步改模块流程 | 从方案起，不做数据源探测，不新建模块 |
| 录制一次写 | [FLOW.md](FLOW.md) 的四步录制流程 | 手动开 `diy-record` 后直接调 `workbench_diy_record_prepare`，不经过 `workbench_diy_plan` |

流程中除方案步外用 `workbench_diy_step` 提交当前节点结果；`done: true` 是唯一完成信号。节点顺序、字段与返回以工具定义为准，[FLOW.md](FLOW.md) 只解释每一步要做什么。

## 跨入口规则

- **工具包**：DIY 默认开 `diy-flow`，流程到 probe / build / verify 时自动开对应包；录制与调试分别手动开 `diy-record` / `diy-debug`。缺哪包由工具返回点名，按返回处理；工具被收起时不换工具重试。`manage` 在 DIY 会话不可用，管理边界见 [FAMILY.md](FAMILY.md)。
- **写闸**：方案确认前及安装、验收时，`write` / `edit` 被收起；创建模块与保存设计记录时放开。`bash` 只用于只读探查与命令执行，不用它写文件绕过写闸。写工具不可用时按返回的当前步与下一步继续。
- **审批**：「加自己的、能撤的」不问；「引外来的、删掉的、占屏的、发出去的」问。模块写能力的声明与材料见 [TOOLS.md](TOOLS.md) §5–§7。
- **必须说话**：构建失败时说「代码已写完但未通过检查，正在修复，不需要你做任何事」，两轮后仍未修复就只说哪项未通过与下一步，不贴报错原文；工具被拒时只有「模块没有显示在面板上」需要告诉用户，其余按返回自行处理；需要重启时只说一次「需要退出工作台再打开一次」，然后等待，不提供无效按钮。
- **判断预算**：看板最多 4 次、无看板最多 3 次内容决策；出草图、改草图、二选一各算一次，复述与「还是这些吗」不计。超过预算就按推荐继续并标注假设；「随便你定」是合法答案。
- **交付**：固定说清安装在哪里（面板第几格，或「已安装到工作台；不提供面板卡片，只提供 agent 工具」）、现在能做的一件事、以后怎么改（「修改某某模块」即可）。无看板还要说上一次运行时间与查看位置。
- **实现边界**：dsh 已有能力从 `kit` 取，不手写 DOM 与 CSS，不直接 import dsh 的包；源码零注释。默认不发布，只有用户明确要求后才走 [WIRING.md](WIRING.md) 的发布段。
