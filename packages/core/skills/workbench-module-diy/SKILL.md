# workbench-module-diy

## 第 0 步：判去向（先做这一步，它能终止整个流程）

用户描述的需求不一定需要模块。先判断去向，再决定问什么、问几次、交付什么。

| 去向 | 判据 | 交付什么 | 询问用户几次 |
|---|---|---|---|
| **用现成的** | 模块市场里有、本机已安装但未添加到面板、或 dsh 已有能力（含定时） | 安装 / 添加到面板 / 直接使用 | 0 |
| **一次性** | 只做这一次 | 结果进对话 | 入口已明 0，否则 1 |
| **改道** | 要改 dsh 本身（创造模式）；或要新凭据 / 新服务 / 新依赖（工程域） | 一句指引 + 一个现在就能用的替代 | 0 |
| **有看板模块** | 每天查看一次，需要一格 | 面板上的一个模块（走下面的阶段） | 判断 ≤4 次 |
| **无看板模块** | 需要它代用户持续跟进或代办，用户不看面板 | 工具 + 一个触发者（[TOOLS.md](TOOLS.md)） | 判断 ≤3 次 |

判据只能是「工作台独有能力的正面清单」——脚本层是超集，永远能做，所以不能问「能不能做」。

九项独有能力（碰到至少一项才可能要做模块）：卡片与五态 / 面板行提示与顺序 / 动作路由（要有卡片，
四条条件缺一不可）/ 长任务（六态、等你处理、侧栏露出）/ 按工作区的模块配置与数据目录 / 站点表
（登录复用、过期信号、信封、分页）/ 流程引擎（轮询、逐项、子流程、agent 节点）/ 模块市场 /
工具包（按需开包）。

不算独有的：**能写**（dsh 也能写文件、运行命令，只有落到那两档写缝才算）、**能运行长任务**（dsh 自己有
后台任务与定时，只有六态与「等你处理」才算）。

三道测试：

1. **剥离** —— 把工作台卸载后，在纯 dsh 里这需求还成立吗？成立 → dsh 侧。
2. **触碰** —— 碰到九项里至少一项吗？一项都没有 → dsh 侧。
3. **目的** —— 碰到的那项是这个需求的目的，还是附带的手段？只是附带 → 剥离后再判断。

输出固定三行，对用户说，不是给 agent 的日志：

> 结论：这件事不需要面板，我直接处理，不新增模块。
> 依据：不需要在面板中占一格、不需要登录站点、不需要等你处理。
> 要调整就说：如果希望以后每天在面板上看到它，我再改为模块。

用词只用用户见过的：**面板**、**模块**。不出现「看板」「长流程」「插件」——「插件」在本仓还指 opencli 插件。

**不确定时往轻处错**：先一次性或先无看板，不要先创建卡片。事后升级成本低，移除则等于重做。

## 每一步交什么

判到「要做模块」之后，流程按格推进，面板上可见。顺序不在这里写（流程定义是唯一来源），
这里只说每一格要交出的东西。

开流程用 `workbench_diy_plan` 与 `workbench_diy_step`；具体参数与返回见 [FAMILY.md](FAMILY.md)。创建时第一次只交去向与一句话复述（不审批）；
修改可直接交完整方案；方案那一步再交完整方案，其余各格逐格提交。文件写入与编辑只在「创建模块」与「保存这次的设计」两格放开；
没开流程时不在工具面里。

| 格 | 你要交出 |
|---|---|
| 查看数据来源 | 站点表（[STEPS.md](STEPS.md)·站点表 + [DATASOURCE.md](DATASOURCE.md) 第 0 段） |
| 确认方案 | 四段（一眼看到 / 你能做 / AI 能做什么 / 数据从哪来）+ 看板的 ASCII 卡片（[DESIGN.md](DESIGN.md) §3） |
| 创建模块 | 站点表 → 接口 → 配方 → 模板 → 构建（[BUILD.md](BUILD.md) §1–§2） |
| 安装 / 添加模块到面板 | `workbench_diy_install`；三种结果各说清：直接生效 / **需要退出工作台再打开一次** / 安装失败 |
| 检查（显示或功能） | 只读取证五态，「验过 / 未验」两列贴给用户，未验必须明写（[REVIEW.md](REVIEW.md)） |
| 保存这次的设计 | 写入设计底稿；模块说明从用户说明生成 |

**判成一次性**（不进流程时）：给一句时间承诺，完成后把结果发到对话中。

**判成改已有模块**走另一条五格：补充方案 → 修改模块 → 热换 → 只验证那一格 →
保存这次的设计。没有站探（数据源没变），也不新建模块。

**判断预算按内容决策算**，不按问句算：出草图算一次，改草图算一次，二选一算一次。复述与
「还是这些吗」不计。超出预算就停止，按推荐走并标注假设。「随便你定」是合法答案，不追问。

**三种情况下一定要说话**（不要让屏幕沉默）：

- **构建失败**：说「代码已写完但未通过检查，正在修复，不需要你做任何事」；两轮仍未修复时再说明「哪一步未通过、
  下一步怎么处理」，不要贴报错原文。
- **工具被拒**：只有一种需要告知用户 —— 模块没有显示在面板上，说「这一步需要先把模块添加到面板」；工具包未开启、
  桌面端没有页面调试这两种，自行解决，不要交给用户处理。
- **要重启**：说「**需要退出工作台再打开一次**」，说完就等，不要再劝、不要给按钮。

**交代**：固定三句话 —— 安装在哪里（面板第几格，或「它没有格子，是一把工具」）；现在能做的一件事；
以后怎么改（说「修改某某模块」即可，先复述上次设定）。

## 流程对 agent 的约束到哪为止

流程运行期间，宿主按当前这一步收窄工具面 —— 只拒 `write` / `edit` 两把，`bash` 从不拒。

- 没开流程时：`write` / `edit` 被拒
- 查看数据来源、确认方案、添加模块到面板、检查模块显示：`write` / `edit` 被拒
- 创建模块、保存这次的设计：放开
- `bash` 一路可用（查看数据来源要用命令，`cat > 文件` 这类写法拦不住）

所以「确认方案之前不动手」是**默认路径上**的约束，不是沙箱。真正的把关点是方案那一步的审批：
用户批准后才开始执行；绕过审批写出的内容，用户必须能在对话里看到。

## 这个会话开哪些包

这份指引只随 DIY 模式出现；下面的「这个会话」都是 DIY 模式的会话。

DIY 模式默认只开 `diy-flow`（状态 / 计划 / 步骤 / 面板 / 查看已安装模块）。其余按流程步自动加开，
只增不减，流程结束或中断时一次收回（手动开的包自己关）：

- 查看数据来源：`diy-probe`（`_recon` / `_spec`）；
- 创建模块：`diy-build`（`_install` / `_publish` / `_show`，外加从管理族借用的 `panels_hide` /
  `modules_install` / `modules_install_bundle` / `modules_uninstall` / `long_tasks_list` / `long_tasks_stop`）；
- 检查模块显示：`diy-page`（页面族与日志）。

`diy-record` 与 `diy-debug` 不自动开：录制前手动开 `diy-record`，调试前手动开 `diy-debug`。
`manage` 在这个会话里不提供，打开会被拒并说明改用哪两族；更新模块、更换实现、安装插件、
修改模块来源、调整面板顺序都不在这里做，请回到普通会话。

Desktop 上 `diy-debug` 与日志那一族不提供；页面族还在，但只走带站点地址的只读线（见「查」）。

审批口径一句话：**「加自己的、能撤的」不问；「引外来的、删掉的、占屏的、发出去的」问。**
所以 `_install` / `_show` / `panels_hide` 不问；安装外部包、卸载模块、停止长任务、开启屏幕调试、录制、发布需要审批。

## 无看板模块的三条硬约束

1. 工具和其它模块一样收在工具包里：用之前先开包（`workbench_toolbox_open`，不审批）；包里的写工具仍逐条问。没有卡片也一样，没有常驻这一档。
2. 必须交付一个**触发者**：dsh 的定时任务，或「你说一句我就执行」。定时能力属 dsh，但「谁触发」
   是这个模块的交付物。
3. 交代里必须说明它上一次运行的时间，以及在哪里查看。

这一档**不建设计底稿的面板表**，也**不运行面板检查**（它要求面板表非空）；替代门禁是构建、模块检查与实际运行一次给用户看。模块说明手写。

## 改已有模块

用户说「这个数不对 / 修改一下」时，不要重新访谈：

1. 读模块根的设计底稿。
2. 复述三行：看什么（`panel[].cell`）/ 哪几格（`panel[]`）/ 什么时候会变（`linkage[].when`）。
3. 只问「还是这些吗，要改哪一条」。

## 查（用户反馈面板不正确时）

按 [REVIEW.md](REVIEW.md) 的四步取证。「查」交付的是「面板现在怎么样」这一事实，不交付技术方案。
要捕获「用户点击之后发送了什么」，依次调用 `workbench_diy_record_prepare` → 用户操作 → `_record_read`；
结束调 `_debug_stop` / `_record_stop`。

> **Desktop**：页面族还在，但只走「带站点地址的只读线」；不带地址的看 / 动 / 网络会被拒绝，并把这条
> 下一步说出来。`diy-debug` 与日志那一族不提供。录制、`_panel`、`_status`、构建与安装照旧。

## 创建落点

模块创建在 `workbench_diy_status` 给出的「工作区：<dir>」下。那里没有可放置代码的包时，请用户二选一：
在这里创建 workspace，还是使用工坊的脚手架工作区。不要改动用户仓库的结构。
从「创建模块」入口进来的会话已经在工坊里。

套模板见 [BUILD.md](BUILD.md) §1–§2：先按模板初始化模块，再修改数据源与渲染。依赖由 setup 安装完成；
确实需要安装时，在**工作区根**运行包管理器（会话沙箱里会报 EPERM）。
不要从零编写。渲染文案按 [COPY.md](COPY.md)：先判读者（卡片给人 / 描述给 agent / 原始输出进 detail）。

## 发布

只在用户说「帮我发布」之后调用 `workbench_diy_publish`。缺更新日志就带变更说明；缺少模块市场标签时，选择 1–2 个短词。
不要手动修改模块清单，不要补标题或署名，也不要询问用户发布出口。发布工具需要用户确认时按返回正文转述。
审批之前会先做一次发布前检查：缺什么就直接拒绝、不显示审批，
按理由补齐后再调用一次。细节见 [WIRING.md](WIRING.md) §5。

## 查不到时

1. 模块工具链的单条判据报错原文。
2. kit、dsh 原语、CSS 令牌、宿主能力与 deps：读对应声明与 JSDoc；需要定位时用当前环境的只读查询面；
   工程域用模块工具链的 kit / primitives 判据。
3. 模板：模块工具包里的模板目录（见 [BUILD.md](BUILD.md)）。
4. 已安装包的类型面与本指引：见已安装包里的 skills 目录（细节见 [BUILD.md](BUILD.md)）。

## 硬约束

- dsh 已有的能力从 `kit` 取；不要手写 DOM 与 CSS，也不要直接 import dsh 的包。
- DIY 模块默认不发布到任何来源；用户确认后才调用 `workbench_diy_publish`。
- 源码零注释（行注释、块注释、样式注释都不许）；用户说明写模块说明，作者说明写开发说明或 spec。
